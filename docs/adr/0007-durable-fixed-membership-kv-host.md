# ADR 0007: Durable Fixed-Membership KV Host

- **Status:** Accepted
- **Implementation:** Complete
- **Date:** 2026-10-04
- **Decision owners:** dotnet-raft maintainers

## Context

The three-node gRPC example demonstrates transport, Ready ordering, proposal
completion, and read-index barriers, but both Raft and application state are
volatile. `DotnetRaft.Sqlite` now provides durable consensus storage; using it
alone would still be unsafe because:

- committed commands can be durable while application state is not yet
  applied;
- application state can be durable before `Advance`;
- accepted bootstrap configuration must be recoverable at the same
  physical-applied index;
- a snapshot can be durable before application restore completes; and
- client retries need a durable request identity to avoid duplicate effects.

## Decision

Convert `examples/DotnetRaft.KvCluster` into a crash-recoverable,
fixed-membership distributed KV host.

1. **Two local durable databases per node**
   - `raft.db` uses `DotnetRaft.Sqlite.SqliteStorage`;
   - `application.db` stores KV state, physical-applied index, application
     `ConfState`, and request deduplication results;
   - both use SQLite WAL, exclusive ownership, and FULL synchronous commits;
   - no cross-database atomicity is claimed;
   - backup and restore treat both databases as one recovery set; the supported
     simple procedure stops the host and preserves the complete data directory
     as one unit; and
   - startup rejects missing/recreated application state and provably
     incompatible cursors/configuration, but cannot prove that every arbitrary
     independently captured pair belongs to the same application generation.
2. **Recovery protocol**
   - reconcile any pending Raft application snapshot first;
   - restore application bytes, physical cursor, and `ConfState`
     transactionally;
   - preserve trusted hard-state term/vote, repair commit only when required,
     and acknowledge the snapshot;
   - validate application configuration against the fixed bootstrap prefix;
   - start a new cluster only when both databases are empty;
   - otherwise restart `RaftNode` with `Applied = physicalApplied`;
   - committed entries above the application cursor are replayed normally;
   - restore a retained Raft snapshot whenever application state is behind it;
   - create a matching local snapshot before restart whenever application
     state is ahead of the retained snapshot but covered by retained log; and
   - admit no external Raft input until all three bootstrap entries are
     physically applied and durably reconciled.
   - if `application.db` was recreated or is missing while `raft.db` is
     nonempty, fail startup; snapshot replay is not allowed to erase the only
     durable local-node identity binding.
3. **Application transaction**
   - every committed entry advances physical-applied exactly once;
   - set/delete effects, request deduplication, configuration state, and
     physical-applied update commit in one application transaction;
   - empty, rejected configuration, and duplicate commands still advance the
     cursor;
   - conflicting reuse of a request ID is a deterministic rejected no-op, not
     a node fault;
   - pending waiters retain the expected command fingerprint, so a different
     committed winner completes them as conflict rather than false success;
   - one shared proposal submission remains live while any identical local
     waiter remains, so cancellation of the first caller cannot strand the
     others;
   - snapshot restore resolves live proposal waiters from the restored durable
     request table; and
   - request rows are retained without pruning and every application snapshot
     includes the complete request table.
4. **Client identity**
   - PUT accepts an optional request ID and returns the effective ID;
   - DELETE accepts an optional request ID;
   - absent IDs are generated by the receiving host;
   - server-generated IDs are explicitly non-retryable after an unknown
     timeout; retry-safe clients must supply and reuse a stable ID;
   - retrying an already applied identical command returns the original result
     without proposing another entry;
   - reusing an ID for different command bytes returns HTTP conflict.
5. **Reads**
   - linearizable reads retain the existing `ReadIndex` barrier;
   - the value and physical cursor are read from the application database in
     one serialized operation;
   - read barriers that arrive ahead of a size-limited committed-entry page
     remain pending until physical application reaches their index;
   - local reads remain explicitly potentially stale; and
   - HTTP request bodies, gRPC, and Raft batching share an explicit 64 MiB
     default message limit;
     oversize commands are rejected before proposal and oversize application
     snapshots are not compacted into an undeliverable recovery point.
6. **Snapshots and compaction**
   - application snapshots contain sorted KV rows, sorted request-dedup rows,
     physical-applied index, and exact `ConfState`;
   - post-Advance snapshots reduce replay, while mandatory startup
     reconciliation closes crashes before Advance or snapshot creation;
   - afterward, snapshots are created when the distance from the retained
     snapshot reaches a configurable threshold;
   - an oversized snapshot attempt advances an in-memory retry cursor so the
     host waits another threshold interval instead of rematerializing the
     entire state after every entry;
   - Raft compaction occurs only after the matching durable application
     snapshot is stored.
7. **Scope**
   - exactly three fixed peers;
   - durable application metadata is bound to one immutable local node ID;
   - set, delete, linearizable get, local get, status, and manual campaign;
   - HTTP and gRPC listeners bind to loopback only and provide no TLS,
     authentication, or authorization; structural Raft message validation is
     not a security boundary;
   - no MVCC history, compare/transaction, watch, lease, auth, dynamic
     membership API, sharding, or etcd wire compatibility.

## Rationale

Raft storage and application storage deliberately remain separate, matching
the WAL/backend split in complete systems such as etcd. Crash consistency is
obtained through durable cursors, replay, idempotent snapshot restore, and
strict compaction ordering rather than an artificial cross-database
transaction.

Startup reconciliation closes the D21 configuration-recovery gap even when a
crash occurs after application commit but before Ready advancement or snapshot
creation.

Durable request IDs make HTTP timeout/retry behavior explicit without placing
client protocol concerns in the consensus library.

## Consequences

### Positive

- A three-node cluster survives orderly restart and abrupt process
  termination.
- Committed-but-unapplied commands are replayed.
- Applied-before-Advance commands are not duplicated.
- Bootstrap configuration, snapshots, and compaction are recoverable.
- Clients can safely retry mutations using a stable request ID.

### Tradeoffs

- Each node performs FULL synchronous writes to both Raft and application
  databases.
- The two databases must be backed up and restored as a compatible recovery
  set; arbitrary independent generations can be valid-looking but semantically
  unrelated.
- The fixed-membership sample remains a single replicated shard; every node
  stores all data.
- Request deduplication history is retained without pruning in the MVP, so
  application storage and snapshot size grow with the number of unique
  mutation request IDs.
- Application snapshots materialize state in memory as required by the
  existing snapshot API.
- Very large state can defer compaction so lagging replicas remain recoverable
  through retained log entries.

## Rejected alternatives

- **Store Raft and application tables in one SQLite database:** couples the
  reusable Raft package to one application schema and hides the real host
  recovery boundary.
- **Keep application state in memory while only persisting Raft:** cannot
  preserve acknowledged writes or snapshot configuration after restart.
- **Advance before durable application:** would require replay semantics that
  can acknowledge client writes before their state is crash durable.
- **Compact only by logical applied index:** can delete entries required to
  recover physical application state.
- **Add MVCC/watch/lease now:** expands the milestone before basic crash
  recovery is proven.

## Acceptance criteria

This decision is implemented when:

1. component tests cover durable set/delete/no-op/configuration,
   deduplication, conflicts, snapshot serialization, restore, and reopening;
2. deterministic integration restarts all three nodes from the same data
   directories and continues linearizable reads/writes;
3. crash-window tests cover Raft-persisted/application-unapplied and
   application-applied/Ready-unadvanced states;
4. pending-snapshot tests terminate after Raft snapshot persistence,
   application restore, commit repair, and acknowledgement boundaries;
5. a real three-process smoke kills and restarts a node, then continues quorum
   operation with the same data;
6. snapshot generation and compaction preserve restart and follower catch-up;
7. full tests, formatting, benchmark smoke, packages, and reproducibility
   remain green;
8. independent GPT-5.6 Sol design and code review has no unresolved
   substantiated finding; and
9. the reviewed change is committed, pushed, and green in CI.

## Implementation evidence

The implementation satisfies the local acceptance gates:

- 998 core/example tests and 33 SQLite tests pass in both Debug and Release;
- the durable three-process SIGKILL, snapshot catch-up, quorum, and full
  restart smoke passes in three consecutive fresh runs with a 31 MiB value;
- focused line/branch coverage is 94.37%/74.59% for
  `SqliteKeyValueStateMachine`, 89.54%/78.78% for `DurableHostRecovery`,
  100%/92.85% for `DurableKvCommandCodec`, 81.96%/76.31% for
  `PendingProposalRegistry`, and 91.66%/87.50% for `PendingReadRegistry`;
- the final pre-review focused mutation run executed 513 mutants: 295 were
  killed, three produced reviewed liveness timeouts, and the remaining
  survivors were reviewed; subsequent review fixes have dedicated regression
  tests rather than another full mutation rerun;
- both benchmark smoke suites retain their expected checksums and allocation
  fields; and
- formatting, package consumers, deterministic package reproduction, and the
  same durable process smoke are enforced by CI.
