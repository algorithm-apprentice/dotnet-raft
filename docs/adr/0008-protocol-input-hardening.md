# ADR 0008: Protocol Input Hardening

- **Status:** Accepted
- **Date:** 2026-10-04
- **Decision owners:** dotnet-raft maintainers

## Context

`RawNode.Step` is the public network-message integration boundary. It already
rejects local-only message types and unknown response senders, but some
structurally invalid messages can still reach `RaftCore`.

The deterministic core treats impossible message shapes as
`RaftInvariantException`. That is appropriate for messages generated by the
library itself, but a host can receive malformed protobuf messages from a
buggy, incompatible, or unauthenticated peer. An empty proposal, a zero-term
vote, an inconsistent append slice, an oversized heartbeat commit, or an
invalid read acknowledgement can therefore fault a `RaftNode` before the
transport can reject the request.

Configuration changes have a related boundary problem. Unknown protobuf enum
values and the two IDs reserved for local storage workers can enter proposals
or restored configurations before semantic application detects them.
`NodeId == 0` is different: the pinned `etcd/raft` behavior treats it as a
configuration no-op and compatibility requires preserving that rule.

The library must reject malformed external input without weakening internal
invariant enforcement or claiming to authenticate network peers.

## Decision

1. **Validate network message structure before core mutation.**
   - `RawNode.Step` validates an owned message before `RaftCore.Step`.
   - Validation covers host-independent protobuf and Raft shape requirements
     that would otherwise surface as invariant or parsing failures.
   - State-dependent checks run only when the current term and role would
     process the relevant leader message or response.
   - Validation occurs before term, role, log, tracker, or output mutation.
2. **Keep internal invariant failures terminal.**
   - `RaftInvariantException` remains evidence of an internal bug, corrupted
     durable state, or an impossible library-generated transition.
   - The implementation does not broadly catch or downgrade invariant
     exceptions.
   - Invalid external input is reported as `ArgumentException`, which the
     concurrent facade treats as a request failure rather than a node fault.
3. **Validate configuration structure at every ingress boundary.**
   - public V1 and V2 proposal APIs reject unknown transition/change enum
     values before appending;
   - network proposals validate embedded configuration entries before core
     dispatch;
   - configuration application and restoration reject
     `RaftLocalMessageTargets.AppendThread` and
     `RaftLocalMessageTargets.ApplyThread` as member IDs; and
   - `NodeId == 0` remains a valid no-op in configuration changes.
4. **Separate structural validation from policy validation.**
   - `DisableConfChangeValidation` continues to control overlapping and
     joint-state proposal admission only.
   - It never disables protobuf structure, known-enum, or reserved-ID checks.
   - A committed configuration that is corrupt or semantically impossible
     remains terminal during application.
5. **Keep authentication in the transport.**
   - Structural validation does not authenticate `Message.From`.
   - The host remains responsible for binding an authenticated peer identity
     to `Message.From`, validating `Message.To`, authorizing membership, and
     restricting listener exposure.
   - The educational gRPC host remains loopback-only and explicitly
     unauthenticated.
6. **Record the parity deviation explicitly.**
   - The pinned implementation relies on its host and generated messages for
     these preconditions.
   - dotnet-raft adds fail-fast validation at its public integration boundary
     because exceptions in the concurrent facade otherwise become terminal
     process-level failures.

## Consequences

### Positive

- malformed peer input cannot fault a healthy `RaftNode` through known
  structural preconditions;
- invalid configuration proposals are rejected before log mutation;
- local storage worker IDs cannot become quorum members;
- internal invariant failures remain visible instead of being hidden by a
  broad recovery path; and
- transports receive a stable request-error category they can map to their
  native invalid-input response.

### Tradeoffs

- `RawNode.Step` performs additional validation and may parse configuration
  entry payloads before the leader processes a proposal;
- some inputs tolerated until later application by the pinned implementation
  are rejected earlier by dotnet-raft; and
- transport authentication remains a separate host requirement.

## Alternatives rejected

### Treat every `RaftInvariantException` as peer input failure

Rejected because an invariant can be raised after internal corruption or a
library bug. Continuing the node would risk silent state divergence.

### Validate only in the gRPC example

Rejected because every `RawNode` and `RaftNode` host needs the same
host-independent structural protection.

### Reject node ID zero

Rejected because zero-valued configuration operations are intentional no-ops
in the pinned behavior.

### Add TLS or a credential model to the core package

Rejected because ADR 0001 keeps transport and deployment identity outside the
consensus library.
